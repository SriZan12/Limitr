# Blocking state and upgrade contract

`BlockingSession` is the source of intended blocking state. Each package has one current revision. Package names, not localized display names, determine identity. A replacement receives a fresh revision; cancellation and notification-option edits use package + revision conditions. Old callbacks cannot delete a replacement, and no receiver writes a session. Different packages can overlap. Start is inclusive and end is exclusive.

`ScheduleEvaluator` is pure Kotlin with an explicit `TimeSnapshot`. New duration timers use elapsedRealtime (including sleep) for the same boot. Persisted wall deadlines are recovery fallbacks after reboot/restore and for old records. Fallback remaining time is capped by original duration and rebased once onto the new boot's elapsed clock. Device clock tampering during a reboot cannot be resolved perfectly without an independent trusted clock. No network clock is introduced. API 24+ uses the system boot count combined with a per-install ID; API 23 uses a boot-receiver token. Clock identity is excluded from backup. Force-stop can suppress that receiver; API 23 reboot while force-stopped remains an unverified recovery edge case.

Intervals remain one-shot windows. Local start/end choices resolve to instants when saved. A passed start moves to the next calendar day; an end at/before start moves to the following day. Calendar arithmetic handles DST (Java time resolves nonexistent local times forward and chooses the earlier offset during overlaps). The UI confirms the resolved dates/times. Later time-zone changes change their display, not the chosen instants. Manual clock changes affect these wall-clock schedules. Reconciled expired rows are removed, so later clock rollback cannot revive them.

`SessionRepository` uses Room transactions for session/history writes and expiry/reboot reconciliation. `SessionCoordinator` observes changes, publishes load/error state, and waits for the nearest boundary using a cancellable coroutine. A non-exact elapsed-realtime alarm requests reconciliation if the process was reclaimed. Boot, package update and clock/time-zone broadcasts do likewise. The alarm is an optimization/recovery hint; it has no stale session payload and cannot activate cancelled rows. Exact-alarm permissions, wake locks, WorkManager countdowns and permanent foreground services are unnecessary here. Under Doze/OEM restrictions callbacks can be late; a newly delivered app-window event evaluates current time before enforcing.

`AppLaunchDetector` holds only the last package event and one service-owned accessibility overlay. It subscribes to coordinator state, so a scheduled start rechecks the last foreground package without requiring an app switch. The service does not retrieve the screen tree to discover a foreground package on initial connection: it reports waiting until the next window event. Overlay countdowns have one cancellable job; expiry, cancellation, screen-off, interruption and disconnect remove the window. The overlay's own events do not replace the tracked package. Essential app events clear the window. System Home/Back/navigation remain accessible. Opening session details requires an explicit user tap.

`EnforcementStatus` separately tracks consent, connection and window errors. UI never equates a saved session with an operational service. Accessibility enabled in settings does not prove connection. Permission restoration, reconnect and app resume reconcile saved state. Task removal, process death and service disconnection are different from force-stop: Android controls reconnect; force-stop cannot be repaired by app code before the user launches again. Multi-window/PiP may expose content even while a selected package lacks focus. This is a voluntary consumer blocker, not OS package suspension.

The notification listener cancels only the selected notification key while its package's session is active and suppression is selected. Essential and ongoing notifications are preserved. It holds one cancellable collection; there are no continuations or permanent LiveData observers. Posting session notifications is optional and permission-gated. Delivery is best effort; missed transitions while the process is absent are not replayed as historical notifications.

## Persistence

Database filename remains `LimitrTable`. Version 13 keeps the old `LimitrTable` and `HistoryTable`, and introduces `BlockingSession`. Migration copies sessions from known Git schemas 3, 4, 6, 7, 8, 9, 10 and 12. Earlier shapes are normalized by adding nullable columns; raw legacy rows/extra columns are retained in `LegacyLimitrTable`. Version 9 has two observed shapes. Missing package identities remain preserved and are reported on the history screen for reselection. Duplicate legacy package rows select the latest blockedTime deterministically; all originals remain archived.

No destructive fallback, renamed database, or silent reset exists. Unknown schema versions (including 5 and 11, not established from source) fail closed: storage-unavailable UI, retained database, no blocking based on invented state. Historical Room JSON exports and actual shipped database samples are unavailable. Tests create source-derived SQLite fixtures and invoke real Room validation; these are not proof of every shipped upgrade. Obtain production samples before rollout. Version 13 schema is exported and checked in.

DataStore filename `Data_Store` and keys `Crypto` / `last_logged_date`, and shared preferences `My SharePref`, remain. Daily reward claims are one atomic edit; repeated taps cannot award multiple same-day rewards. The existing 2-Crypto unblock shortcut remains; confirmed Stop session permits intentional cancellation without credits. Crypto and Room use separate stores: a process death between cancellation and debit can grant a free unblock, but never charge before a successful cancellation. This is a local convenience reward, not a financial asset.

## Authentication removal

Firebase/Google sign-in, analytics, database/storage dependencies, plugin and config files are removed. The published application ID (`com.khadka.Limitr`) and component namespace (`com.khadka.limitr`) are restored from master. Local schedules/rewards never had account-specific ownership in the existing code and remain device-local. The profile uses local preferences and Android's document picker; cloud-only name/photo are not fetched. No remote account/project/security rules were changed or deleted. Owner must maintain a remote-data deletion/support process and update the published privacy policy. Backup includes local databases/settings, excluding auth credentials, accessibility consent and device-clock identity.
